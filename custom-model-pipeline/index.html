    Custom Model Pipeline

    This proposal shows how to build a self-service system that lets customers teach new object classes to their camera AI. Customers give images. The system labels them, fine-tunes a model, tests it and installs it on their Frigate system. The proposal also answers one question: should you use the Frigate source code from GitHub or the Docker image?

    Chapters
      00

      Short answer

      Decision 1

      Use the Docker image

      Run the unchanged Frigate image at each customer site. Do not fork Frigate. Put your code in separate containers that talk to Frigate through its API and its files.

      Decision 2

      Two layers, not one

      Use the classification layer that Frigate 0.18 already has for sub-classes. Fine-tune the detector only for object types that the base model cannot find.

      Decision 3

      Apache-2.0 models

      Train RF-DETR (Nano, Small, Medium), D-FINE or YOLOX. Their licenses permit a commercial service. Do not use Frigate+ models or their API.

      Use the GitHub source code only to read how Frigate works and to run compatibility tests. If you change Frigate itself, you must rebuild and test your fork for each Frigate release. You also must rename the fork if you distribute it. A separate service avoids both problems.

      WARNING

      Do not use the name "Frigate" or "Frigate+" in the name of your product, app or domain. The Frigate trademark policy prohibits this for commercial products. You can say that your product is "compatible with Frigate" or "works with Frigate NVR".

      NOTE

      "Free for the customer" does not mean "free to operate". Each training run uses GPU time, and you must store images and models. Chapter 08 shows a mode where training runs on the customer's own GPU. In that mode, you pay almost no compute cost and the images stay at the customer site.

      01

      System overview

      The system has three parts. The site is the customer's Frigate computer with one extra container, the model agent. The platform is your service that labels, trains and tests models. The app is where the customer adds classes and approves results.

      02

      03

      Two learning layers

      A "new class" can mean two different things. The correct layer depends on one question: can the base detector already find the object?

      The classification layer is the "class layer on top of Frigate" that you asked about. It already exists in Frigate 0.18, so you do not have to write it. Your work is to automate it: collect crops, sort them into classes and start training through the API.

      The detector layer is the part that Frigate+ sells. You must build it yourself. It is the main subject of chapters 06 and 07.

      Request from the customerLayerFrigate output
      "Tell me when it is my dog, not the neighbor's dog"Classification (object, sub_label)dog with sub label Rex
      "Mark persons who wear a helmet"Classification (object, attribute)person with attribute helmet: yes
      "Tell me when the garage door is open"Classification (state)MQTT frigate/<cam>/classification/garage_door
      "Detect forklifts in my warehouse"Detectornew label forklift
      "Detect my company's logo on vans"Detector (attribute label)new attribute label, set in model.attributes_map

      04.1Correct use of the GitHub code

      • Read it. Use the source to learn the exact model input and output formats (frigate/util/model.py, frigate/detectors/).
      • Test against it. Your CI pulls the Frigate image, loads your exported model and plays a test clip (chapter 12).
      • Contribute to it. If you need a small, general change (for example a better hook for model updates), send a pull request to the Frigate project. Do not keep a private fork.
      05

      Site integration: the model agent

      The model agent is a small container that runs next to Frigate in the same Docker Compose project. It is the only new software at the customer site.

      05.1Compose file

      services:
  frigate:
    image: ghcr.io/blakeblackshear/frigate:stable   # unchanged
    volumes:
      - ./config:/config
      - ./media:/media/frigate
    # ... devices, shm_size, ports as usual
  model-agent:
    image: ghcr.io/<you>/model-agent:1.0
    restart: unless-stopped
    environment:
      FRIGATE_URL: http://frigate:5000          # internal port, same Docker network
      PLATFORM_URL: https://api.<your-domain>
    secrets: [site_token]
    volumes:
      - ./config/model_cache/custom:/models      # model files only
      - ./config/config.yml:/frigate/config.yml:ro
      - ./media/clips:/clips                       # classification datasets
secrets:
  site_token: { file: ./site_token.txt }
      WARNING

      Port 5000 has no authentication. The agent must reach it only on the internal Docker network. Do not publish port 5000 on the host. The agent must make only outbound connections to the platform.

      05.2Frigate API calls the agent uses

      TaskFrigate 0.18 endpoint
      Find candidate objectsGET /api/events?has_snapshot=1&labels=…&after=…

      Save the configurationPOST /api/config/save?save_option=saveonly (YAML body)

      05.3Automate the classification layer

      Frigate keeps each classification dataset in /media/frigate/clips/<model>/dataset/<class>/. The agent can put verified crops in these folders and then start training through the API. No Frigate change is necessary.

      1. Add the model to the Frigate configuration one time, for example classification.custom.dog_id with object_config.objects: [dog].
      2. The customer adds classes in your app ("Rex", "Bella", "none").
      3. The agent gets crops of dog objects from the events API. The app shows them to the customer to sort.
      4. The agent writes the sorted crops into clips/dog_id/dataset/<class>/.
      5. The agent calls POST /api/classification/dog_id/train. Frigate trains on its CPU in 1–3 minutes.
      6. Frigate sets the sub label on new dogs. MQTT frigate/tracked_object_update sends each result.
      classification:
  custom:
    dog_id:
      threshold: 0.8
      object_config:
        objects: [dog]
        classification_type: sub_label    # or attribute

      05.4Install a custom detection model

      Frigate loads any model file from model.path. A Frigate+ model is only a file in /config/model_cache plus a JSON file with its input settings. Your agent writes the same information directly into the model section.

      detectors:
  ov:
    type: openvino                    # or onnx for Nvidia / AMD
    device: GPU
model:
  model_type: rfdetr                 # or dfine, yolox
  width: 320
  height: 320
  input_tensor: nchw
  input_dtype: float
  path: /config/model_cache/custom/site42-v7.onnx
  labelmap_path: /config/model_cache/custom/site42-v7.labels.txt
objects:
  track: [person, car, forklift]   # add the new label here
  filters:
    forklift: { min_score: 0.55, threshold: 0.75 }   # from the evaluator
      CAUTION

      The output layout of your exported model must agree with Frigate's decoder for that model_type. For example, Frigate's RF-DETR decoder ignores output class 0 and takes the class with the highest softmax score. Use the export method from the Frigate documentation, and test each export in the stock image before release.

      06

      Training pipeline (detector layer)

      The pipeline changes customer images into a tested model file. Each stage has one input and one output. Each stage keeps its output, so you can repeat any later stage without the earlier ones.

      06.1Collect and select

      • Sources. The agent gets snapshots and full frames through the Frigate API. The customer also uploads photos in the app.
      • Uncertain objects. Select events with a top score between min_score and threshold. The model is not sure about these. They teach it the most.
      • Wrong results. The customer marks false positives in the app. Keep them as negative examples. Frigate+ advises about 80% true positives and 20% false positives.
      • Coverage. Take images from each camera, by day and by night, and in different weather.

      06.2Clean

      Remove near-identical frames. A tracked object makes many similar frames. Keep a small number of frames from each event. Remove images that are too blurred or too small. Apply privacy rules before upload, for example blur faces when the customer does not need face classes.

      06.3Auto-label and verify

      Do not ask the customer to draw every box. First, the current model labels the classes that it knows. Then an open-vocabulary detector, which accepts a text prompt such as "forklift", proposes boxes for the new class. The customer only accepts, moves or deletes boxes in the labeling tool.

      WARNING

      Auto-labels are suggestions. Train only on images that a person verified. Wrong labels make a bad model, and more training does not repair them.

      06.4Freeze the dataset

      • Give each dataset a version number and store a manifest: image IDs, label IDs, class list, split.
      • Split by camera and by event, not by frame. If frames from one event are in the training set and in the validation set, the test result is too optimistic.
      • Keep a fixed validation set for each customer. Use the same set to compare each new model with the current model.
      • Add a replay set of public images for the base classes (person, car, …). This keeps the model good at the old classes.

      06.5Training recipe

      ItemRecommendationReason
      ArchitectureRF-DETR Nano or Small; D-FINE S; YOLOX for NPUsApache-2.0 license, Frigate 0.18 decoders exist
      Start weightsPublic COCO checkpoint of the same modelFine-tuning needs much less data than training from zero
      Input size320×320Frigate sends 320 px regions. The Frigate docs recommend 320 for almost all users.
      Training imagesSquare crops around objects (1.35× to 2× the object size), plus some full framesThis is the same kind of image that Frigate sends to the detector at runtime
      AugmentationInfrared grayscale, motion blur, JPEG noise, brightnessSecurity cameras have night mode and compression
      Class listBase classes that the customer uses + new classesA smaller list is faster and has fewer false labels

      06.6Evaluation gate

      The evaluator decides whether a model can go to the customer. Use rules like these. Set the exact values from your own tests.

      1. Each new class reaches the agreed quality on the fixed validation set (for example, recall of 0.8 at precision 0.9).
      2. No base class becomes worse than the current model by more than an agreed limit (for example, 2 points of mAP).
      3. Inference time on the customer hardware stays inside the budget (chapter 10).
      4. The exported file gives the same boxes in the stock Frigate image as in the training code.

      For each class, the evaluator also calculates suggested values for min_score and threshold from the precision-recall curve. The agent writes them into objects.filters.

      07

      Model delivery and rollback

      A bad model can stop a security system from seeing people. Thus the agent installs a model in steps, and it can always go back to the previous model.

      07.1Procedure: install a model (agent)

      1. Download the model and its manifest to a temporary folder.
      2. Verify the SHA-256 hash and the signature. If one fails, delete the files and report the error.
      3. Run the shadow test on saved clips. Send the results to the app.
      4. Wait for approval from the customer and for the maintenance window.
      5. Make a copy of the current YAML file and the current model file.
      6. Move the new files to /config/model_cache/custom/.
      7. Change the model and objects sections. Save with POST /api/config/save?save_option=saveonly.
      8. Restart Frigate with POST /api/restart.
      9. Check /api/stats each minute for 30 minutes, then each hour for 24 hours.
      10. If Frigate does not start, or the health check fails, restore the copy and restart.

      08

      Where training runs

      Training needs a GPU. You can supply the GPU (cloud mode) or use the customer's GPU (local mode). Build the training worker as one container image, so the same code runs in both modes.

      ItemCloud modeLocal mode
      Where images goYour object storageStay at the site
      Who pays for the GPUYouThe customer (their own hardware)
      Customer hardwareAny Frigate computerNvidia GPU with enough memory for training
      LabelingYour hosted labeling toolLabeling tool in the app, images streamed from the site
      Shared base modelPossible, with consentNot possible
      Best forSmall sites, Intel N100 or Coral usersPrivacy-sensitive users, "no subscription" promise
      NOTE

      Start with cloud mode for your first customers. It is easier to debug. Add local mode when the pipeline is stable. The evaluation gate and the model registry stay the same in both modes.

      Per-customer model or shared model. Frigate+ fine-tunes from a base model that was trained on images from all subscribers. You can do the same only if each customer agrees that you can use their images for all customers. Without that consent, fine-tune each customer's model from the public checkpoint and use only that customer's images.

      WARNING

      Public datasets have their own terms. For example, COCO images come from Flickr with different licenses for each image. Before you use a public dataset for a commercial model, read its terms. This proposal is not legal advice. Ask a lawyer before launch.

      09.2Trademark

      • Do not put "Frigate" in your product, app or domain name.
      • Do not use the Frigate logo.
      • You can write "compatible with Frigate NVR" or "works with Frigate".
      • Do not say or show that Frigate, Inc. supports or approves your product.

      09.3Privacy

      Camera images show people, faces, number plates and homes. In most countries these are personal data. Follow the data protection law of each customer's country. Examples are the Digital Personal Data Protection Act 2023 in India and the GDPR in the EU.

      • Get clear consent for each use of the images: training for that customer only, or training of a shared model.
      • Upload only the images that the customer selects. Never upload video streams.
      • Encrypt images in transit and at rest. Delete them when the customer asks or when the retention time ends.
      • Offer local mode for customers who must keep all images at their site.

      Hardware targets

      Each detector type in Frigate needs a different model file. Support the easy targets first. Each new target needs its own conversion step and its own tests.

      Frigate detectorHardwareFile from your pipelinePhase

      CAUTION

      A model that is fast on a GPU can be too slow on a small computer. RF-DETR Nano at 320 takes approximately 40 ms on an Intel NPU and approximately 90 ms on an AMD 9060XT with ROCm (Frigate hardware page). For each customer, record the hardware in the app and select a model size that fits the inference budget.

      11

      Customer app

      The app is the only part that the customer uses directly. Keep it simple: one screen for each step of the loop.

      ScreenFunction
      SitesConnect a Frigate site with a one-time code. Show agent status, Frigate version and detector hardware.
      ClassesAdd a class. The app asks questions and selects the layer (Fig. 03-1).
      InboxImages that the agent selected. The customer accepts or rejects each one, or marks it as a false positive.
      LabelAuto-labels shown as suggestions. The customer accepts, moves or deletes boxes, then verifies the image.
      TrainShows the count of verified images for each class. The Train button is active only when each class has enough data.
      ResultsEvaluation report: quality for each class, compared with the current model, sample images with errors.
      DeployApprove a model, set the maintenance window, see the rollout state, roll back with one action.

      Build the app on the platform API only. Do not connect the app directly to the customer's Frigate. Thus the customer does not have to open Frigate to the internet.

      12

      Roadmap

      12.1Procedure: phase 0 proof

      1. Select one new class that the base model cannot detect, for example "forklift".
      2. Collect 200–500 images from the target cameras. Include day, night and empty scenes. (This count is a starting estimate.)
      3. Label every object in each image in CVAT or Label Studio. Export in COCO format.
      4. Fine-tune RF-DETR Nano from the public checkpoint at 320×320 with the classes person, car and forklift.
      5. Export to ONNX with the method that the Frigate documentation uses for RF-DETR.
      6. Write the label file. Put both files in /config/model_cache/custom/.
      7. Set the model section as in 05.4. Add forklift to objects.track.
      8. Add a dummy camera that plays a test clip (Frigate Field Manual, chapter 12).
      9. Look at the Debug view. Make sure that Frigate detects the forklift and still detects persons.
      10. Write down the inference time from System > Metrics.

      12.2Compatibility tests in CI

      Run these tests for each new model and for each new Frigate release:

      1. Pull ghcr.io/blakeblackshear/frigate:stable.
      2. Validate the configuration with python3 -u -m frigate --validate-config.
      3. Start Frigate with a dummy camera and a known clip.
      4. Read /api/events. Compare the labels and the count with the expected result.

      Decisions and risks

      13.1Decisions you must make

      1. Hardware. Which detectors do your customers use? This sets the phase 1 targets.
      2. Training location. Cloud mode, local mode, or both?
      3. Data use. A model for each customer only, or a shared base model with consent?
      4. Business model. Who pays for GPU time, storage and support?
      5. Product name. A name without "Frigate".
